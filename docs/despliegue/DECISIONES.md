# Registro de decisiones técnicas: plataforma Docker

Estado: implementada y verificada en EC2 de pruebas el 16 de noviembre; pendiente de revisión del equipo. Fecha: 16 de noviembre de 2026. Alcance: un condominio, una VM y un volumen de fotos local. Esta entrega no modifica las reglas del Product Owner ni despliega automáticamente.

| Decisión | Motivo, consecuencias y límites |
|---|---|
| Ubuntu Server 24.04 LTS como contrato del bootstrap | Base mantenida, APT y systemd conocidos; misma operación para equipo Windows/Linux porque la ejecución final se encapsula en contenedores Linux. Amazon Linux requiere otro instalador. El dry-run también se puede usar desde Linux de desarrollo, sin cambiarlo. |
| Docker Engine + Compose, una VM | Operación y coste adecuados para una entrega académica pequeña. Evita introducir Kubernetes/ECS/RDS antes de necesitar escalado. Es un único punto de fallo; no ofrece alta disponibilidad ni reemplaza una política de backup. |
| Node 24 Alpine en ambos proyectos | Mantiene la versión mayor declarada y reduce el runtime. Se probaron bcrypt, sharp y Prisma en musl/amd64 con las imágenes reales; ARM64 sigue pendiente de validación. `npm ci` usa el lockfile. Build por etapas separa herramientas de compilación y ejecución. |
| Imágenes base fijadas por digest | `deploy/base-images.env` y los Dockerfiles evitan que una etiqueta móvil cambie una release. Los digests multi-arquitectura seleccionan el binario para el host; no convierten una imagen amd64 ya construida en ARM64. Actualizar digests por PR y reconstruir. No se afirma que un digest garantice ausencia de vulnerabilidades. |
| PostgreSQL 18 Alpine | Mismo major usado en las pruebas funcionales. Volumen montado en `/var/lib/postgresql`, respetando el PGDATA versionado de la imagen 18. No reutilizar sin migración un volumen PG16/17 ni cambiar el major con un simple pull. |
| Caddy como único ingreso | Automatiza emisión/renovación HTTPS, redirección HTTP y proxy conservando Host/protocolo. Cookies Secure y Server Actions funcionan con el mismo origen sin ampliar allowedOrigins. No se expone directamente REST/Swagger; los handlers y acciones de Next hablan con API por la red privada. HTTP/1.1 y HTTP/2; no requiere UDP/443. |
| Next standalone, SSR real | Las sesiones, Server Actions y Route Handlers requieren servidor; una exportación estática perdería esos flujos. Copiar `.next/standalone`, `.next/static` y `public`. `API_URL` es runtime, exclusivamente de servidor, sin `NEXT_PUBLIC`. El build descarga las fuentes de Next/font; necesita Internet. |
| Persistencia explícita | Volúmenes separados: BD, `/uploads`, certificados y configuración de Caddy. Cache/tmp de Next y API en tmpfs, prescindibles. No se empacan fotos en imágenes ni se publican como estáticos: siguen pasando por autorización y los handlers privados. No se añade S3 para fotos porque cambiaría la implementación de almacenamiento y su alcance. |
| Redes y puertos | Redes application y database internas; gateway también se conecta a edge para ACME. Solo gateway publica TCP80/443. API accede a BD pero web no se conecta a database. La API no tiene salida directa a Internet; email es NiceToHave y no se configura proveedor SMTP. Añadir una integración futura exige revisar egress. |
| Privilegios por servicio | API y web: usuario node UID1000, filesystem de solo lectura, `cap_drop: ALL`, `no-new-privileges`, init y cierre con gracia. Caddy conserva solo NET_BIND_SERVICE; su proceso y el entrypoint de PostgreSQL usan root inicialmente según sus imágenes oficiales, por eso no se afirma que todos los procesos sean no-root. Ningún contenedor usa privileged o Docker socket. |
| Tres identidades de BD | `postgres` solo dentro de BD para inicialización/backup; `sonnet5_owner` en migración para DDL; `sonnet5_app` en API/admin/catálogo para CRUD, sin superusuario/CREATEROLE/CREATEDB ni CREATE en public. Default privileges otorgan futuras tablas/secuencias, pero `_prisma_migrations` queda explícitamente revocada tras migrar **y restaurar**. El runtime necesita acceso CRUD amplio a las tablas de negocio; la autorización por residente sigue en NestJS, no se implementó RLS. |
| Secretos como archivos concedidos por servicio | Cinco valores independientes: PostgreSQL root, owner, app, JWT y password inicial ADMIN. Compose local usa mounts de archivos, no un vault cifrado. El directorio host es root0700 y los archivos0444 para que UID1000 pueda leer el mount; no confiar en uid/mode overrides de secretos respaldados por archivo. El entrypoint construye DATABASE_URL con encoding seguro solo dentro del proceso. Docker inspect no recibe la URL/password/JWT resueltos en Config.Env, pero root/Docker y el proceso autorizado sí pueden acceder a ellos. |
| Migración como tarea explícita de arranque | `migrate deploy` termina correctamente antes de API. No se usa `db push`, reset ni migración dev en producción. Aplicar migraciones desde la misma imagen que API evita divergencias. Se mantiene Prisma CLI en dependencias de producción porque se ejecuta en esa tarea; separar una imagen de migración adicional queda como optimización futura. Un fallo requiere intervención; nunca se baja el esquema automáticamente. |
| Healthchecks con responsabilidades separadas | PostgreSQL comprueba SELECT1 real por TCP; API readiness comprueba SELECT1 con su cliente; Next `/api/health` es liveness. No publican credenciales, stacktraces ni estado de usuarios. Compose espera cada dependencia en el arranque y la herramienta hace un GET HTTPS final. Un 200 del frontend no demuestra por sí solo salud permanente de la base. No hay orquestador que reinicie por unhealthy. |
| Límites de recursos y logs | API1GiB, web768MiB, BD768MiB, gateway128MiB; tareas puntuales512MiB. Topes iniciales para una VM4GiB, no reservas ni medición de capacidad. Node tiene heap inferior al tope del contenedor para dejar espacio nativo. BD limita conexiones a40 y shared_buffers128MiB. Logs json-file rotan3x10MiB por contenedor; sin sistema de observabilidad nuevo. |
| SHA de ambos repos y manifiesto por release | El cambio necesita una pareja compatible de fuentes. `deploy` clona commits completos aprobados, build secuencial o pull por digest, valida revisión OCI y registra IDs de imagen. `up` rechaza un tag local cuyo ID cambió. No mueve develop ni hace merge/auto-deploy. Los PR son encadenados porque los funcionales anteriores siguen abiertos. |
| Python stdlib para operación; Bash para preparar host | Python permite parsing sin eval, validación de rutas, lock, JSON atómico, checksums y control de errores. Bash se limita a APT/UFW/systemd/secretos con fail-fast. Boto3 se instala desde Ubuntu y solo se usa si se configura S3; credenciales por IAM role. No se descarga y ejecuta un instalador remoto con curl\|sh. |
| Backup consistente con pausa de escrituras | Parar web/API coordina SQL y fotos antes de pg_dump/tar. El proceso reanuda escritores con finally; lock excluye despliegues simultáneos. Pausa visible, normalmente breve; programada a03:00 El Salvador con systemd, sin depender del contenedor de la aplicación. Backup diario implica un RPO de hasta24h si todas las copias se completan; RTO no medido ni garantizado. No hay PITR/WAL archive. |
| Restore explícito; rollback de código condicionado | Verificar hashes y tar sin rutas externas/enlaces, SQL en transacción y app detenida. Backup de confianza: los checksums detectan corrupción, no autentican a quien lo modifica. PostgreSQL y fotos no tienen una transacción común; recuperar manteniendo tráfico cerrado si falla la segunda fase. El operador confirma restauración y compatibilidad del esquema antes de reabrir con rollback. No se automatizan downgrades SQL. |
| Backup S3 opcional fuera del servidor | Upload con SSE-S3, IAM limitado al prefijo, sin claves en repositorio. Copia local retiene7d por defecto; retención S3 se administra en bucket. La subida fallida no elimina copia ni ejecuta retención. La configuración local y secretos requieren custodia separada: no se incluyen junto a datos en S3. No se probó acceso AWS real. |
| Hardening limitado al servidor dedicado | UFW permite22 por CIDR y80/443; conserva reglas existentes y protege contra excluir la sesión SSH actual. Security Group es obligatorio porque publicación Docker puede eludir UFW. No se altera sshd ni se agrega el usuario al grupo docker. Instalar actualizaciones de seguridad de Ubuntu sin reinicio automático evita interrupciones inesperadas; planificar reinicios y parches de contenedores. |
| Bootstrap sin demo ni datos inventados | Crea un solo administrador; catálogo real separado, validado e idempotente. No se ejecuta el seed existente con cuentas/contraseñas de demo. Los datos sintéticos de pruebas se generan exclusivamente en un proyecto Docker aleatorio local. |
| TLS y cabeceras sin excepciones globales | TLS público con validación normal, nosniff y Referrer-Policy; límites Caddy20MiB/Next16MiB. No imponer CSP, HSTS preload o trust-all que no se hayan validado con los recursos actuales. CA local solo en localhost/loopback de tests; Playwright acepta ese certificado en esa suite y Python sí valida su cadena. |

## Riesgos y decisiones pospuestas

- No se automatiza AWS por IaC: esta entrega configura un **servidor existente**. Faltan crear EC2, red, DNS, IAM y bucket conforme a la cuenta y presupuesto del equipo.
- Bootstrap real en Ubuntu/EC2 y ACME público ya se comprobaron en el despliegue de pruebas. Recuperación en un host perdido, S3 real y arquitectura ARM64 requieren ensayo operativo. Dry-run y dobles de prueba no sustituyen esas comprobaciones.
- La VM y sus volúmenes son un punto único de fallo. No hay replicación, despliegue sin interrupciones, balanceador, autoscaling ni garantía de capacidad o coste.
- Para varias réplicas se necesitaría almacenamiento de fotos compartido, coordinación de tareas programadas y una estrategia de caché/sesión. En esta entrega se ejecuta una API y una web.
- Mantener respaldos verificados y una release recuperable; no limpiar volúmenes ni imágenes automáticamente. Ensayar la restauración periódicamente. La privacidad de datos reales exige control de acceso y ciclo de vida en sus copias.
- Los PR funcionales conservan la validación temporal de Actions solicitada previamente. No se reemplazó esa CI por un supuesto despliegue automático; los resultados completos de esta entrega son locales.
