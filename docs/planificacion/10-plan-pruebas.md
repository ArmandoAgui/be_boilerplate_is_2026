# Plan de calidad y matriz de pruebas trazables

> Edición para revisión en el fork, publicada por solicitud posterior del equipo. La arquitectura, estimaciones y asignaciones siguen siendo propuestas. Las referencias a conservación local, ausencia de commits/push y «esta ejecución» describen la etapa de planificación anterior; esta publicación posterior incorpora la documentación sin modificar aplicación ni protecciones.

**Estado:** planificación propuesta, no implementación ni decisiones aprobadas. **Alcance confirmado por el equipo:** diez módulos más adaptación de autenticación; cinco integrantes; cuatro semanas.

## Estrategia y niveles

**Plan propuesto; ninguna prueba nueva está implementada o ejecutada.** Reutilizar Vitest/Supertest del backend. Tests unitarios para reglas puras, integración real con PostgreSQL de desarrollo aislado para restricciones/transacciones, contratos API para permisos y recorridos manuales reproducibles de UI. El frontend no trae framework de pruebas; aprobar herramienta solo si automatizar recorridos justifica su coste. La prueba manual debe registrar pasos/datos/resultados, no solo una captura.

Fixtures candidatos: condominios A/B; dos torres en A; unidades A-101/A-102 y B-101; residentes R1/R2 en A-101 y R1 también en A-102; R3 solo en B-101; administrador de A y seguridad de A. La facultad de representación de R1/R2 se define por D-08 para comprobar voto concurrente. Estos datos no se insertan con esta planificación.

Cada prueba funcional exige sesión/roles adecuados de HU-T-04/05 y datos de desarrollo. Verificar respuesta API, datos persistidos después de recarga y estado visible. No exponer tokens, contraseñas o datos reales en evidencia. Criterios CA se consultan también en [01-alcance-y-requerimientos.md](01-alcance-y-requerimientos.md).

## Ejecución propuesta y criterios de salida

Cada dueño implementa/ejecuta sus PR funcionales y un revisor reproduce el criterio principal. Los PR-S-01/03/06/09 se ejecutan con solicitudes simultáneas sobre PostgreSQL, no mocks que no apliquen restricciones; PR-S-08 cubre renovación. Guardar cantidad de filas, estados de ambas respuestas y resultado después de recarga.

Semana 1: PR-T y primer flujo; semana 2: funcionales de M1/2/3/4/5/7/8 y bandeja; semana 3: M6/9/10 y productores reales, alternativas; semana 4: PR-S completo y regresión de todos los RF. Se pueden automatizar antes los casos de mayor riesgo; no esperar al final para concurrencia o permisos.

No aceptar PR con fuga entre unidades/roles, doble voto/reserva/entrega, saldo incoherente o criterio obligatorio omitido. Para la entrega: todos los 29 RF y sus criterios demostrados, PR críticos aprobados y demo accesible. Un bloqueo externo se documenta y eleva; no se marca como aprobado un test no ejecutado. Defectos visuales menores pueden priorizarse sin ocultar impacto, por decisión del equipo.

La e2e existente monta AppModule y consulta `/`, sin bootstrap de main: no cubre el prefijo/pipes de ejecución completa ni la plataforma. El reporte final debe distinguir prueba de reglas, contrato, UI e integración real.
